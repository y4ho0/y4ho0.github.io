关于分布式数据库，经常能看到简单的二分法：“关系型数据库强调一致性，NoSQL 强调可用性”；或者“只要 W + R 大于 N，就能保证强一致性”。

这些口诀有助于记住术语，却不足以分析真正的系统。读一个数据是否能看到最新值，取决于故障模型、操作语义、复制协议、并发写入处理和实际客户端路径。

## 首先区分三种不同的“一致性”

**ACID 的 Consistency**：数据库事务前后保持系统所定义的约束和不变量，例如外键、唯一性约束或业务约束。ACID 中的另外三项是原子性、隔离性和持久性。

**分布式系统的 Consistency**：讨论并发读写在多副本之间能否呈现某种单一历史。一个常见严格模型是线性一致性（Linearizability）：已完成写入之后开始的读，应反映该写入或更新的更晚状态。

**最终一致性（Eventual Consistency）**：在更新停止且系统能够继续传播更新的前提下，副本最终趋于一致。它不自动保证读己之所写、单调读或线性一致性；这些都是需要明确描述的额外语义。

同样叫“一致性”，不先说清所指模型，就容易得出错误结论。

## CAP 真正在讨论什么？

CAP 中的一致性通常按线性一致性理解；可用性是有关有效请求是否获得成功响应的性质；网络分区意味着节点组之间的消息可能丢失或无法通信。

**关键前提是发生了网络分区。** 此时系统需要在继续提供所有期望的成功操作与维持严格一致性之间做出取舍。不能据此得出一个永恒的产品标签：“MySQL = CA”“HBase = CP”“某种数据库 = AP”。

同一产品在不同拓扑、复制与读写配置下，行为可能不同。日常无分区情况下的延迟与可用性取舍，也不能完全用 CAP 解释。

## W + R > N 为什么不等于自动强一致？

某些基于副本 quorum 的设计使用：

- N：复制因子；
- W：写入确认需要的副本数量；
- R：读取采样的副本数量。

当 W + R > N 时，在理想的固定副本集合里，读写集合有交集。这有助于构造某些一致性保证，但**集合交集本身不证明线性一致性**。还要看并发写的排序、版本冲突处理、读修复、节点变化、故障恢复及协议细节。

例如，两个并发写入是否按统一规则排序？读取到多个版本时如何决定哪一个是最新？复制成员变化期间是否仍满足原来的交集假设？这些问题没有回答，就不能把不等式直接当成全系统的强一致性证明。

尤其不能将 HDFS 的写入确认直接套进所有 Dynamo 风格数据库使用的 W/R/N 模型；其复制与文件语义不同。

## BASE 是什么，ACID 又是什么？

BASE 是 Basically Available、Soft State、Eventual Consistency 的缩写，用来概括某些分布式系统更宽松的数据收敛策略。

它不是与 ACID 完全对立的“另一种四字事务标准”，更不代表所有 NoSQL 都没有事务。具体产品可能支持单文档、单行或多文档事务，也可能在不同操作上提供不同隔离与持久化保证。

现实工程首先看使用场景：订单结算、库存扣减和资金状态通常需要明确的正确性约束；缓存、搜索索引和分析视图在一些情况下可以接受一定传播延迟。

**“是否使用 NoSQL”不能替代对一致性、事务及业务不变量的分析。**

## 一个有用的工程提问清单

面对具体数据库或复制架构，应优先明确：

1. 成功写入的承诺是什么？已经持久化到几处？
2. 紧随其后的读取可能走主节点、从节点还是任意副本？
3. 网络分区时，哪一侧能继续接受读和写？
4. 并发更新发生冲突时，谁决定顺序？
5. 故障恢复之后，如何防止旧状态覆盖新状态？

这些问题比“CP 还是 AP”的孤立标签更接近实际设计与面试讨论。

## 知识来源与核对边界

《云计算与大数据》第 5 章覆盖 NoSQL 类型、CAP、BASE、最终一致性及 W/R/N 复制配置。上述内容保留了这些知识主题，但**对将数据库产品静态分类、将 W+R>N 直接等同于强一致性的简化表述增加了限定条件**。这是进一步比较分布式语义后做出的补充，并非逐句复写讲义。
