“大数据应用”并不是把 Hadoop 生态中的所有组件装到同一套系统里。面对一个业务问题，更有用的顺序是先明确数据如何产生、需要多快得到结果、查询形态是什么，以及错误或重复处理是否可以接受。

以下用三个抽象场景说明技术取舍，不将这些例子描述成真实部署案例。

## 场景一：每天统计一批历史日志

输入已经落盘，结果可以在小时级或天级生成。重点往往是吞吐、单位数据处理成本、可重试性和可追溯性。

典型处理链路可以是：

~~~text
历史日志文件 → 批量读取 → 清洗与聚合 → 查询结果
~~~

MapReduce 是经典的分布式批处理模型。现代数据分析还经常使用 Spark 等计算引擎处理 SQL、批计算或其他分析任务。计算引擎与底层存储不必绑定为一套固定部署：同一份数据可能位于分布式文件系统或对象存储中。

不应把“离线分析”简单等同于“只能使用 Hadoop MapReduce”。

## 场景二：持续接收设备或用户事件

事件不断到来，没有天然的“文件结束”时刻。系统可能需要按时间窗口统计、处理乱序和迟到数据，并在故障后恢复处理状态。

典型链路：

~~~text
事件生产方 → 消息/事件日志 → 流计算 → 物化结果或告警
~~~

Kafka 提供事件发布、持久化与订阅等能力；Flink 重视有状态流计算、事件时间和检查点；Spark Structured Streaming 则提供在结构化 API 下进行增量流处理的能力。它们承担的职责不同，未必需要同时引入。

流系统的技术选择必须考虑：事件可能延迟多久、允许多长处理延迟、状态有多大、失败后是否重放，以及下游系统是否支持幂等或事务写入。

## 场景三：按主键低延迟查询或更新

在线接口希望根据唯一标识快速返回记录，可能需要修改状态并向调用方确认。

这种需求不适合每次收到请求就启动一个离线 MapReduce 作业。更应关注数据模型、主键布局、索引、事务、读写延迟与故障切换。

关系数据库与 HBase 等系统的适用性，需要结合查询、容量、一致性和运维要求讨论。

例如交易状态变更涉及业务不变量：同一交易不能因为重试而重复扣减。消息传输的重试机制并不会自动替业务消除重复副作用。无论使用哪种数据系统，消费端幂等、状态约束和端到端确认语义都需要独立设计。

## 一张简化的选型表

| 核心需求 | 优先考察的能力 | 常见技术方向 |
| --- | --- | --- |
| 可延迟完成的大规模计算 | 批处理吞吐、查询优化、成本 | MapReduce、Spark、SQL 引擎 |
| 持续事件处理与时间窗口 | 有状态计算、时间语义、检查点 | Flink、Spark Structured Streaming |
| 事件持久化、解耦与重放 | 分区、日志保留、消费管理 | Kafka 等事件平台 |
| 大规模按键访问 | 主键与分区设计、随机访问 | HBase 等存储系统 |
| 业务事务与复杂关系查询 | ACID、索引、约束、隔离级别 | 关系数据库 |

这不是产品排行榜，也不能仅凭一行需求确定最终技术栈。数据规模、团队能力、已有基础设施和合规要求都可能改变答案。

## 回到知识体系

HDFS、MapReduce、YARN、HBase 展示了一个经典的数据系统如何把存储、计算、调度和在线访问分开。现代系统继续沿着类似问题演进，但实现方式更加多样。

因此理解 Hadoop 的价值，不止在于会执行 hdfs dfs 命令，而是在面临新的数据系统时能够判断：它解决了哪个瓶颈，又引入了哪些失败模式和工程成本。
