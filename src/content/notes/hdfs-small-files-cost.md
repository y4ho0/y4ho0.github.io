假设有两批数据：一批是少量大文件，另一批是上百万个几 KB 的文本文件。它们的总字节数可能相近，但放进 HDFS 后，对系统的压力未必相同。

HDFS 的典型目标是高吞吐地存取大规模数据集，而不是像通用本地文件系统那样高效管理极其零碎的文件。问题的关键不只是小文件占了多少磁盘，而是**每个文件都需要独立的命名空间和块元数据**。

## 一个常见误解：1 KB 文件会占满一个 128 MB 数据块吗？

假设某个 HDFS 文件系统配置的数据块大小为 128 MiB。

一个 1 KiB 的文件通常不会因此在 DataNode 上实际写入 128 MiB 的有效文件内容。**块大小是文件分块的上限及管理粒度，而不是每个小文件必须预占的完整物理空间。** 同时，副本数和文件系统实际存储开销也会影响占用。

但不管它只有 1 KiB 还是 50 MiB，只要它是独立文件，NameNode 就必须管理它的目录项及相应块信息。

简化表示：

~~~text
文件 A：1 KiB   ──> 一个文件条目 + 一个块相关记录
文件 B：1 KiB   ──> 一个文件条目 + 一个块相关记录
文件 C：1 KiB   ──> 一个文件条目 + 一个块相关记录
...
~~~

多出的一百万个文件，意味着 NameNode 需要处理大量元数据条目，而不是简单将一个大文件切成一百万段。

## 为什么 NameNode 的内存会成为问题？

NameNode 把用于在线服务的命名空间与块映射信息放在内存中。文件和目录越多，需要长期保留的对象、引用和索引就越多。

在 JVM（Java Virtual Machine，Java 虚拟机）中，每个对象除了业务字段，还存在对象头、引用、对齐及相关容器的开销。文件元数据也不一定只对应一个 Java 对象。

因此，即便全部文件实际内容加起来不算大，海量小文件仍可能让 NameNode 堆内存、垃圾回收（GC，Garbage Collection）以及元数据操作承受压力。

需要分清楚两件事：

- **业务上必须保留的对象**：只要文件还存在，相关元数据就不能随意回收；
- **内存泄漏**：对象已经没有业务用途，却因为意外引用而长期无法回收。

HDFS 小文件问题主要是前者，不等于 NameNode 存在程序错误。

## 读写小文件还会增加什么成本？

除了内存，小文件还会影响访问模式。

读取一个大文件时，客户端通常可以持续读取多个较大的数据块；大量独立小文件则意味着反复进行文件打开、元数据定位以及请求处理。

在批处理系统中，输入拆分、任务数量、调度和文件打开开销也可能进一步放大这种问题。不过实际代价与输入格式、合并策略和计算框架有关，不能简单断言“一文件必然一任务”。

这里必须避免没有依据的量化：**小文件比大文件慢多少倍**不能只靠架构图推算，需要固定文件总量、大小分布、副本数、客户端和任务配置，再做基准实验。

## 如何在现有伪分布式环境中观察？

之前的实验已经使用 Hadoop 2.7.1 完成目录创建、-put、-get、-ls、-cat 与 -mv。那些少量测试文件证明功能可用，但不足以证明海量小文件性能。

可以先从无破坏性的状态查询入手：

~~~bash
cd /usr/local/hadoop
./bin/hdfs dfs -count -h /user/hadoop
./bin/hdfs dfs -du -h /user/hadoop
./bin/hdfs dfsadmin -report
~~~

- **-count** 统计目录、文件和逻辑字节数；
- **-du** 查看路径下内容的数据量；
- **dfsadmin -report** 查看 DataNode 的容量及运行状态。

这些命令可说明“文件数量”和“数据体积”是两个不同维度，却不能仅凭一次输出测量 NameNode 中每个 Java 对象的成本。

## 小文件只能合并吗？

不一定。设计上有几条不同路径：

1. **在生产数据流程时避免生成过量碎片**：控制分区和输出文件数量；
2. **适当合并小文件**：适合后续以顺序扫描为主、单文件独立访问需求不高的负载；
3. **选择更匹配的数据组织形式**：例如面向分析的数据集通常还需要考虑列式存储、分区和压缩等手段；
4. **重新评估存储系统**：如果需求是大量小对象的低延迟随机访问，HDFS 可能根本不是最合适的底层接口。

是否合并，取决于访问方式、更新要求及数据处理链路。把所有小文件粗暴合成一个巨型文件，也可能牺牲定位、并行和独立管理能力。

## 回到问题本身

HDFS 的“海量数据”优势，不能直接等同于“海量独立文件”。

系统需要管理多少字节的数据，和需要管理多少文件、目录、数据块，是两个不同的问题。后者对 NameNode 的内存和元数据处理能力尤其关键。

在真正进行优化前，首先要测量的是文件数量、大小分布、块数与实际访问模式，而不是看到小文件就默认升级机器内存或修改块大小。
